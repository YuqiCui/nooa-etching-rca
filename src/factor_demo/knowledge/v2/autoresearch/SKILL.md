# Autoresearch

你负责理解目标、规划、委派和验收证据，并维护一份研究 JSON，使下一步决策和最终交付都能追溯到实际检查。字段与嵌套结构见[研究 JSON 说明](references/research-state.jsonc)，本文只写说明之外的执行约定。

主链：`hypotheses → validation_plan → result.validation_results → result.hypothesis_results → review`。检查执行完成（`validation_results[].status`）、假设得到支持（`verdict`）和主 agent 验收通过（`review.status`）分别记录，三者不能互相推出。

## 目标与立项

- 从用户请求确定总体目标、对象、输入、交付要求、资源约束和停止条件，写入 `goal`。把“有效”“改善”“解释”等词转成可检查的含义，明确比较对象和结论层级。
- 初步分析只用于核对数据范围、版本、对象或独立样本粒度、单位和限制。已确认内容写入 `data_summary`，未知项明确标记。深入分析优先委派。
- 有明确问题时围绕它研究。开放探索时自行选择方向，兼顾用户价值、区分解释的能力、预期信息增量与成本。只对会实质改变问题或解释的缺失信息澄清，其余自行决定并记录假设。
- 资源按实际实验、复核和重试计算，不用打包任务隐去消耗。
- 每个边界明确的调查建一个 `researches[]` 项，分配稳定 `id`，初始 `status=planned`、`result=null`、`review.status=pending`。不同方向可以并存，不为同一结果重复立项。

## 假设与检查计划

- `hypotheses` 按需要区分主要解释、替代解释、伪差和稳健性主张，不必凑齐角色。允许多个解释同时成立，也允许没有胜出者。
- 每项关键检查在执行前写入 `validation_plan`，分配稳定 `id`，写好 `decision_criteria`。阈值、指标或比较协议按当前问题确定，不从示例继承固定数值。没有合理数值门槛时，使用可检查的定性标准。
- 计划要保留可能不利于主要解释的结果。只证明现象存在，不能代替对替代解释和伪差的区分。引用既有结果作为依赖前，核对其输入、方法和证据是否适用。
- 看到结果后提出的新解释使用新假设 ID，不改写原假设去贴合结果。
- 方法、比较口径或判别依据实质修订时，把旧计划、旧结果和修订原因移入 `history`，修订后的检查使用新的检查 ID。核对下游依赖及其结果是否仍适用，失效结果归档后再更新 `depends_on`。迟到的旧 ID 结果只归档，不写入当前结果。事后标准不得写成事先预测。

## 委派

先保存研究项与计划，再标记 `in_progress` 并派发。

- 执行或具体复核任务通过 `agent__spawn` 的 `skills` 预加载 `research-executor`，按需加上领域或方法 skill，用 `allow_tools` 限定工具。
- 任务正文写明 `research_id`、分配的检查 ID 及其计划条目（关联假设、`decision_criteria`、输入版本、范围、方法、依赖证据、`deliverables`），以及资源限制和本任务独立的产物位置。只传必要背景。
- 子 agent 在约束内选择实现。需要改变对象、主要方法、比较口径或判别标准时，由它交回原因和影响，你决定是否修订计划。
- 独立检查可以并行。有依赖的检查在依赖结果可用后再派发。
- 要求子 agent 按 `research-executor` 的格式返回：`research_id`、每个分配检查的 `validation_results` 条目、`limitations` 和 `next_proposals`。子 agent 可以建议判定，不做全局验收。

子会话的 finish 结果会自动投递到当前会话，需要全文时用 `agent__read_result` 分页读取。每收到一份结果就合并并推进可继续的工作，不必等所有并行任务结束。长代码、大表和完整日志保留为可访问引用。

本 skill 加载在子会话时，只执行父任务指定的范围和角色并返回本任务结果，不接管总体目标，不改写父 agent 的全局 JSON。没有委派能力时，按同样边界自行执行，并如实说明没有独立复核。

## 合并结果

- 按 `research_id` 和检查 ID 合并到 `result.validation_results`。不属于当前计划的 ID，包括修订前的旧 ID，不并入当前结果，必要时归档并注明。
- 返回中缺少某个已分配检查时，该检查保持非完成状态，在 `summary` 写明未返回，再决定补派、重派，或记为 `failed`/`skipped`。被取消的子任务按同样方式处理。
- 依赖检查为 `failed` 或 `blocked` 时，下游检查不得按其前提成立来执行或判定。下游检查记为 `blocked` 并写明依赖 ID，或在修订计划后重新派发。
- 部分结果到达即可建立 `result`。暂无内容的列表为 `[]`，未生成报告时 `report_path=null`。
- 不用后来的成功结果覆盖其他检查的失败或阻塞。未执行、失败、超时和不可读取的结果不记为 `completed`。

## 假设判定

`result.hypothesis_results` 由你形成，`verdict` 的取值和含义见 schema。`reason` 说明哪些检查支持判断、哪些构成反证、还缺什么。完整交付覆盖全部假设，未得到有效检验的记为 `inconclusive`。

- `not_supported` 不等于 `refuted`。无法有效检验不等于否定结果。
- 各解释分别判断，主要解释失效不能直接推出替代解释成立。例如，随机划分有效而跨批次不稳定，本身不足以证明批次泄漏。
- `result.summary` 回答本研究问题，`limitations` 保留适用范围、反证和未解决缺口。文字摘要不能替代逐项结果及其 ID 关联。

## 验收

子 agent 自报成功、互相赞同或格式完整都不构成验收。可以委派具体复核或独立复算，最终 `review` 只由你决定。对影响结论的检查核对以下几项：

- **来源**：输入、版本、范围与执行记录对应计划。核心证据要能用你现有的工具实际读取，父会话读不到的子会话本地路径不算证据。
- **计算**：样本量、筛选、分母和单位一致，按影响程度抽查原始材料或复算。不同输入或协议的数值不能直接拼成改善结论。
- **方法**：代码落实了声明的方法，预处理、连接、分组、排除与划分没有改变比较含义。
- **判别**：按执行前的 `decision_criteria` 联合评估主要解释、替代解释、伪差和稳健性结果，未检查的保留为缺口。
- **边界**：差异、关联、预测效果、机制和因果结论的强度与证据匹配。

文件存在、代码可运行或结果可重跑，只说明具备追溯或复现条件，计算语义仍需核查。

- 研究 `status=completed` 只在约定检查和材料完成后使用。可靠的负面或不确定结果可以 `accepted`，关键材料缺失不能用“不确定”掩盖交付不完整。
- 发现错误时记 `needs_revision`。修订开始后研究设为 `in_progress`，旧判定和旧验收归档到 `history`，受影响假设恢复 `inconclusive` 并清除失效的 `validation_ids`，新材料重新验收。
- 证据不可读时，补足可读材料或记为 `blocked`，不写成已验证。

## 持续研究与保存

- 每次验收或出现重要新证据后，判断当前问题的解决程度和下一方向的价值。关键缺口可检验时深化，问题已充分回答时转向，缺乏增量或必要条件时收尾或记录阻塞。不以任务数、运行次数或正面结果数衡量进展。
- 接续研究时用 JSON 定位当前问题和依赖，不回放完整会话。状态摘要不能代替关键证据核查，原始材料按需读取。
- 后续建议写入 `result.next_proposals`，你采纳后才创建新研究项。纠正原问题时沿用原研究 ID，保留旧证据和修订记录。
- 目标或输入改变时，检查受影响结论，重置其验收并说明原因。

主会话是全局 JSON 的唯一写入者。计划、结果、验收、阻塞、修订和结束发生变化时同步保存：

- 用 `record__get` 读取文档和版本，修改后以该版本作为 `record__put` 的 `expected_revision`（新建为 0）。版本冲突时重新读取，按研究和检查 ID 合并后再写，保留其他研究、不利结果和扩展字段。写入是否成功以工具实际返回为准，文件写入同样如此。
- 版本号只用于条件写入，不写进研究正文。记录文档不等于物理 JSON 文件。
- 缺少持久化能力时，返回可保存的 JSON，并明确说明尚未写入。

## 结束与交付

总体目标已得到足够回答、继续研究预计难有增量、资源达到约束，或缺少必要条件且无法继续时，可以结束，并说明真实原因。单项完成不代表总体目标完成，资源耗尽不代表问题解决。

结束前处理已返回的结果，对活动子任务收尾或用 `agent__cancel` 取消，并记录对应检查的状态。核对每个判定都能沿检查 ID 追溯到可读证据，状态属实，JSON 已保存。

通过 finish 交付研究 JSON 的内容或可访问位置，并回答总体目标：已经知道什么、依据是什么、边界在哪里、哪些工作未完成。用户要求文件时，提供实际导出的 JSON 文件，不能只给内部记录标识。可以交付可靠的负面发现或仍未解决的问题。
